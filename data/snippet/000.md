The Directive Status API and its underlying Cloudflare D1 Ledger form the
critical edge-native nervous system of the "Generative Production Pipeline",
decoupling execution state from ephemeral chat channels and local Git trees.
Historically, relying on Slack for merge receipts resulted in "operational
amnesia," while stamping status tags directly into local Markdown files
triggered circular webhooks, polluted Git history, and violated the "Immutable
Causality Principle" of historical specifications. By migrating state tracking
to a hot, serverless relational database, the architecture achieves zero-commit
state tracking, sub-5ms edge querying, and strict ephemeral lease authority.

### 1. The D1 Directive Ledger Schema & State Machine

The structural core of this infrastructure is the `directive_runs` (and
historically `directive_queue`) SQLite table operating within Cloudflare D1.
This schema maps the exact execution lifecycle of every file without relying on
non-deterministic parsing:

- **Composite Identifiers & Ordering:** The `id` string (e.g.,
  `"day-004/024.health-check.jules"`) explicitly binds the file, while a
  composite index on `(day_folder, sequence_num)` guarantees deterministic,
  sequential querying.

- **Tripartite File Typology:** The `file_type` column strictly enforces the
  operational boundary: `'JULES'` for cloud agent mutations, `'GRAVITY'` for
  local agent actions, and `'AG_TEST'` for adversarial verification gates.

- **Finite State Machine (FSM) Enforcement:** The `status` column utilizes
  strict `CHECK` constraints to lock transitions into valid states:
  `'PENDING', 'DISPATCHED', 'PR_OPEN', 'VERIFYING', 'AG_TESTING', 'PASSED', 'MERGED', 'BLOCKED', 'HALTED', 'ROLLED_BACK'`.

- **Cryptographic & Idempotency Bindings:** The table records `pr_number`,
  `candidate_sha`, and `merge_sha` to immutably link the D1 row to GitHub. It
  also utilizes an `idempotency_key` (UUIDv7) to prevent double dispatch or hung
  runs during distributed network partitions.

### 2. The Directive Status API Edge Mounts

To pipe this relational truth to user interfaces, `apps/worker` exposes a suite
of REST endpoints that serve as the interface for the local terminal and web
dashboards:

- **`GET /api/directives/summary` (The Badging Engine):** This endpoint
  aggregates row states per `day_folder` and emits one of three discrete UI
  badges:

- **`[COMPLETE]`**: All directives detected in the folder have been squashed and
  merged into `main`.

- **`[IN-FLIGHT]`**: At least one directive is actively executing (`CLAIMED`,
  `PR_OPEN`, `AG_TESTING`) or has triggered a failure.

- **`[QUEUED]`**: Zero directives within the folder have initiated execution.

- **`GET /api/directives/:day_folder/next-task` (Sequential Dispatch):** When an
  operator engages a day folder, the worker evaluates the sequence array,
  identifying the first row where `status != 'MERGED'`, and streams that exact
  specification back to the terminal.

- **`POST /api/directives/revert-to-seal` (The "Red Button" Reset):** This
  endpoint executes a hard rollback to a verified "Sunset Seal". It accepts a
  `targetDay` and `targetCommitSha`, updates all D1 records for subsequent days
  to `'ROLLED_BACK'`, appends the `failure_reason`, and inserts a
  `SEAL_HARD_RESET` event into the audit log.

### 3. The Tri-Store Checkpoint Architecture

The D1 ledger is not an isolated database; it acts as the primary "Hot Ledger"
within a Tri-Store architecture designed for absolute resumability:

1. **Edge Hot Ledger (Cloudflare D1):** Serves as the single source of truth for
   shift progress, tracking active lease epochs and current statuses.

2. **GitHub Remote State:** Open pull requests preserve in-flight Jules
   mutations, while closed and merged PRs provide immutable cryptographic
   receipts.

3. **Local File System Atomic Checkpoints:** Antigravity testing environments
   write volatile output to temporary files (e.g.,
   `data/reports/.tmp_verdict.json`), committing them to the workspace via
   atomic rename only once validation clears, eliminating corrupted files
   resulting from abrupt crashes.

### 4. Downstream Interface Integration

The "Generative Production Pipeline" dictates that this API drives two distinct
observability layers:

- **The Descending Day Selector (Blessed TUI):** The local terminal harness uses
  `/api/directives/summary` to populate a dynamic Curses menu. It lists the
  `data/directive/day-xxx` directories in descending numerical order, painting
  each line with the real-time D1 badge, allowing the operator to instantiate
  the headless tripartite execution loop (`*.jules.md` $\to$ `*.ag-test.md`)
  directly from the CLI.

- **The Astro Observability Cockpit:** Hosted on Cloudflare Pages, the Astro
  server (`studio.yourdomain.com`) utilizes `@astrojs/cloudflare` to query the
  D1 `directive_queue` directly. This creates a zero-latency "Directive
  Pipeline" visual board (e.g., `DirectivePipeline.tsx`) using React islands,
  bypassing GitHub's REST API rate limits entirely and providing the showrunner
  with a real-time flight deck of the entire studio fleet.

### Phase 1: Data Definition (DDL) & Ledger Architecture

- **[TASK-1.1] Refactor `tasks` and `task_attempts` Tables**
- _Detail:_ The original flat `directive_runs` schema overwrites historical
  attempt data (branch names, head SHAs, failure reasons) during retries. Split
  this into a 1-to-many relationship: a `tasks` table for the primary directive
  (tracking `current_attempt_number` and `current_status` for hot queries), and
  a `task_attempts` table tracking individual execution branches, epochs, and
  SHAs.

- **[TASK-1.2] Implement the `task_events` Append-Only Audit Trail**
- _Detail:_ Create a table to log every FSM state transition. Schema must
  capture `(from_state, event, to_state, actor, reason, epoch, timestamp)`. This
  provides the forensic data required to replay a task's exact history during
  debugging.

- **[TASK-1.3] Implement the `approvals` Ledger**
- _Detail:_ Create an `approvals` table with a uniqueness constraint on
  `(task_id, head_sha)`. This ensures human sign-offs (the `AWAITING_APPROVAL`
  gate) are consumed exactly once and cannot be replayed or applied if the
  `head_sha` mutates.

- **[TASK-1.4] Enforce SQLite `CHECK` Constraints and Indexes**
- _Detail:_ Add database-level `CHECK` constraints on numeric ranges
  (`attempt_numbers >= 1`, `max_attempts >= 1`). Add composite indexes for the
  reconciler (`status`, `updated_at`) to prevent full table scans as the ledger
  scales.

### Phase 2: The Finite State Machine (FSM) Core

- **[TASK-2.1] Define the Executable FSM Transition Matrix**
- _Detail:_ Implement `src/fsm/transitions.ts` containing the exhaustive

- **[TASK-2.2] Implement the `validateTransition()` Choke Point**
- _Detail:_ Create the pure function that accepts `(from_state, event, actor)`

- **[TASK-2.3] Build the FSM Property-Based Test Harness**
