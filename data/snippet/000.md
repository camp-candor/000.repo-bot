### 1. The D1 Directive Ledger Schema & State Machine

The structural core of this infrastructure is the `directive_runs` (and
historically `directive_queue`) SQLite table operating within Cloudflare D1.
This schema maps the exact execution lifecycle of every file without relying on
non-deterministic parsing:

- **Composite Identifiers & Ordering:** The `id` string (e.g.,
  `"day-004/024.health-check.jules"`) explicitly binds the file, while a
  composite index on `(day_folder, sequence_num)` guarantees deterministic,
  sequential querying.

- **Tripartite File Typology:** The `file_type` column strictly enforces the
  operational boundary: `'JULES'` for cloud agent mutations, `'GRAVITY'` for
  local agent actions, and `'AG_TEST'` for adversarial verification gates.

- **Finite State Machine (FSM) Enforcement:** The `status` column utilizes
  strict `CHECK` constraints to lock transitions into valid states:
  `'PENDING', 'DISPATCHED', 'PR_OPEN', 'VERIFYING', 'AG_TESTING', 'PASSED', 'MERGED', 'BLOCKED', 'HALTED', 'ROLLED_BACK'`.

- **Cryptographic & Idempotency Bindings:** The table records `pr_number`,
  `candidate_sha`, and `merge_sha` to immutably link the D1 row to GitHub. It
  also utilizes an `idempotency_key` (UUIDv7) to prevent double dispatch or hung
  runs during distributed network partitions.

### 2. The Directive Status API Edge Mounts

To pipe this relational truth to user interfaces, `apps/worker` exposes a suite

The **Autonomous Edge Maintenance Daemons (Cron Engine)** subsystem transforms
`000.repo-bot` from an event-reactive webhook listener into a continuously
running, self-governing studio custodian. By embedding scheduled executions
directly into the Cloudflare Workers V8 runtime, the architecture eliminates the
need for external cron servers, polling GitHub Actions, or local crontabs.

Crucially, it resolves a major anti-pattern in traditional CI/CD:
state-polluting commits. Instead of committing `digest_state.json` files back
into the `main` trunk to maintain cross-run state, all ephemeral and historical
maintenance state is tracked invisibly within Cloudflare D1 SQL ledgers.

Here is an exhaustive breakdown of the cron engine's underlying mechanics,
distributed safety measures, and the five specific scheduled daemons that keep
the fleet synchronized.

---

### I. Edge Execution Mechanics & Distributed Fencing

To survive Cloudflare's strict 50ms CPU execution limits and distributed Anycast
network behavior, the execution chassis operates on three structural pillars:

#### 1. Scheduled Multiplexing via `ctx.waitUntil(...)`

The edge multiplexer (`apps/worker/src/index.ts`) catches the cron expressions
defined in `wrangler.jsonc`. Because complex GitHub API audits demand
long-running asynchronous network I/O, tasks are delegated to background isolate
contexts using `ctx.waitUntil(...)`. The edge runtime immediately returns a
successful "tick" acknowledgment, while the worker isolate continues processing
the network payload in the background until the promises resolve.

#### 2. Independent Isolate Memory Contexts

When multiple cron triggers overlap (e.g., at midnight UTC, when `0 0 * * *` and
`0 * * * *` collide), Cloudflare provisions entirely separate, independent V8
isolates for each expression. They do not queue, and they share no memory heap.
A memory overflow during a heavy Git drainage will never cause an Out-Of-Memory
(OOM) crash in the concurrent pin-drift auditor.

#### 3. Distributed Idempotency Leasing

Cloudflare Workers Cron Triggers guarantee _at-least-once_ delivery, meaning
overlapping edge routers may occasionally fire duplicate events. To enforce
_exactly-once_ execution, every daemon initiates a `acquireCronLease` handshake
with the D1 database:

- The worker truncates the current timestamp to the exact minute boundary and
  attempts an atomic `INSERT INTO cron_executions` with
  `ON CONFLICT DO NOTHING`.

- If the database returns `success: false`, it means another node won the race.
  The current worker yields silently at $0.00 compute cost, preventing duplicate
  branch deletions or duplicate commit chains.

### II. The Five Operational Edge Daemons

#### 1. Hourly Lockfile Pin Drift Auditor (`0 * * * *`)

Executing every hour at the top of the minute, `crons/pinVerifier.ts` ensures
that all decoupled repositories in the studio point to matching, canonical
states.

- **The Zero-Clone Strategy:** Cloning Git repositories into 128 MB RAM is
  impossible. Instead, the auditor performs pure HTTP operations via the GitHub
  REST API (using `env.GITHUB_TOKEN`), parsing `versions.json` and asserting
  that listed SHAs match the active remote branch HEADs.

- **API Rate-Limit Preservation:** To prevent exhausting GitHub's 5,000
  requests/hour limit, repository checks are executed in strictly bounded,
  concurrent slices ($\le 5$ parallel requests). If the quota drops below 20%,
  it forces a yield.

- **Compilation Invariant Defense:** A silent point of failure occurs when a
  writer edits a raw Markdown file (e.g., `characters/silas.md`) but forgets to
  compile it. The daemon checks Git timestamps: if the source text post-dates
  the artifact ($t_{\text{md}} > t_{\text{json}}$), it logs an "Uncompiled Canon
  Drift" warning to Slack and blocks downstream builds.

- **Auto-Remediation:** If drift is validated against a stable release, the
  worker autonomously dispatches a Jules agent to cut a `spec/TASK-BUMP` branch,
  update the dependency hashes, and submit a PR.

#### 2. Daily 03:00 UTC GC Sweeper (`0 3 * * *`)

At 03:00 UTC, `crons/sweeper.ts` runs a rigorous 4-layer garbage collection pass
across Git, Storage, and D1.

- **Layer 1: D1 Lease Triage:** Queries `execution_leases` for `ACTIVE` tasks
  where `expires_at < now`. If `attempt_count < max_attempts`, the job is
  requeued. If max retries are hit, the job is quarantined to the Dead-Letter
  Queue (DLQ), and an Error Trajectory Vector
  ($\vec{E} = \langle \text{Domain}, \text{Target}, \text{RuleID}, \text{Tokens} \rangle$)
  is posted to `#ops-bridge`.

- **Layer 2: Remote Branch Obliteration:** Enumerates all `refs/heads/spec/*`
  and `feat/*-repair` branches on GitHub. If a branch's HEAD commit is $\ge 48$
  hours old, has _no_ open pull requests, and has _no_ active D1 execution
  leases, the worker executes a forceful `DELETE /git/refs/heads/...` to
  maintain a pristine remote ref space.

- **Layer 3: R2 Scratch Hygiene:** Purges temporary artifacts, latent noise, and
  intermediate patches from the `staging/` and `ephemeral/` prefixes in
  Cloudflare R2 if they are $> 24$ hours old.

- **Layer 4: Idempotency Pruning:** Deletes exhausted transport UUID locks older
  than 7 days from the D1 database to prevent infinite storage bloat.

#### 3. Daily 09:00 UTC Accountability Sweeper (`0 9 * * *`)

The velocity auditor (`crons/velocitySweeper.ts`) combats solo-developer drift
by calculating elapsed time since the last authenticated commit on `main`.

- **Staleness Math:** It calculates the Normalized Staleness Multiplier:

$$M_{\text{stale}} = \frac{\Delta t_{\text{elapsed}}}{W_{\text{repo}}}$$

Where $W_{\text{repo}}$ is the declared check-in window (e.g., 48 hours for core
engines, 168 hours for configs).

- **Progressive Friction:**
- **Quiet** ($1.0 \le M_{\text{stale}} < 2.0$): Silent tracking in D1.

- **Stale** ($2.0 \le M_{\text{stale}} < 3.0$): Posts a polite warning to
  `#ops-bridge`.

  `ShotCoordinatorDO` (a Durable Object). This single-threaded V8 isolate acts

The **"Sunset Seal" Verification Protocol** (also known as the "Long Rest
Protocol" borrowed from tabletop mechanics) is the foundational architectural
boundary that terminates the daily cycle of feature churn and transitions the
system from mutable experimentation into an immutable historical record. In a
generative production pipeline, human labor and machine synthesis operate under
a strict transactional lifecycle: **Allocation (Morning Intent) → Mutation (Day
Shift Execution) → Settlement (The Sunset Seal)**. Without this explicit
terminal boundary, unbounded software projects and generative pipelines decay
under continuous speculative churn, introducing late-night drift, unverified
patches, and circular dependencies that erode system predictability.

### 1. The Four-Tier Structural Pre-Sealing Gate

Before an operator can execute the sunset action and close a workday shift, the
`repo-bot` control plane enforces an automated, non-bypassable pre-flight gate
to ensure systemic stability.

- **Tier 1: Relational Completeness (D1 Ledger):** The edge database must verify
  that every task registered for the current `day-xxx` folder has reached a
  verified terminal state (`MERGED` or `PASSED`). If an orphaned task remains in
  `RUNNING` or `AG_TESTING`, the seal rejects immediately.

- **Tier 2: The Porcelain Zero-Dirty Invariant:** The working directory must
  pass `git status --porcelain` with an empty string output (0 dirty bytes).
  Zero uncommitted files, untracked test fixtures, or transient build outputs
  are permitted to pollute the `main` trunk.

- **Tier 3: The Static & Dynamic Gauntlet:** The full monorepo compiler battery
  (`npx tsc -b`) must exit with code `0`. Furthermore, modified paths are
  scanned for multi-byte Unicode/UTF-8 emojis to prevent terminal and buffer
  corruptions.

- **Tier 4: Boundary Quarantine Assertion:** The diff auditor verifies that core
  frameworks (such as `apps/995.library/`), shared continuous integration
  workflows (`.github/`), and root configuration files have sustained zero
  mutations during the day's tasks.

### 2. Anatomy of the Seal Marker (`.sealed`) & Commit Manifest

To make the sunset tangible, verifiable, and discoverable without querying edge
databases, the sealing engine mints a concrete `.sealed` manifest directly
inside the target day directory (e.g., `data/directive/day-004/.sealed`).

The JSON schema strictly defines the cryptographic anchors and invariant
receipts:

- **Cryptographic Anchors:** Records the `sealed_at` timestamp,
  `operator_signature`, `base_sha`, and `final_sha`.

- **Clearance Roster:** An array of `directives_cleared`, detailing the sequence
  ID, file path, task type, PR number, and `merge_sha` (or local `commit_sha` /
  test `verdict`) for every executed task.

- **Invariant Receipts:** A boolean matrix proving that `clean_tree`,
  `zero_emojis`, `tsc_exit_code`, and `immutable_roots_preserved` passed
  successfully.

Following manifest generation, the local runner executes an Ed25519-signed Git
commit permanently stamping the episode's state mutations and the `.sealed` file
directly into the canonical Git ledger using the Conventional Commit format:
`release(day-xxx): seal shift [3/3 directives cleared]`.

### 3. Edge Ledger Reconciliation & Accountability Sweeper Dormancy

Pushing the seal commit to `origin/main` triggers the final phase: synchronizing
the edge control plane and disarming automated monitoring alarms.

- **Hot-to-Cold Synchronization:** The local runner dispatches a
  `POST /api/directives/day-seal` webhook to `repo-bot`. The edge updates the
  day's status to `SEALED` in Cloudflare D1. This hot operational transaction
  log is linked into the cryptographic SHA-256 hash chain, preparing it for the
  00:00 UTC asynchronous cold-drain cron (`archiveDrain.ts`), which sanitizes
  tokens via RFC 8785 canonicalization and commits `.ndjson` audit logs to an
  orphaned `audit-log` Git branch.

- **Resetting the Dormancy Sweeper:** The daily Accountability Sweeper cron
  monitors commit intervals to catch stalling projects. The successful push of a
  day-closing commit updates the repository's `pushed_at` timestamp in D1,
  resetting the dormancy timer and verifying studio health.

- **Disarming Watchdog Alarms:** The `ShotCoordinator` and `GlobalCoordinator`
  Durable Objects receive the seal receipt, call `storage.deleteAlarm()`,
  release any held financial reservations, and clear active watchdog timeouts to
  prevent false alarms while the engineering room is offline.

- **The Observability Broadcaster:** A final, high-signal Block Kit card is
  posted to `#ops-bridge`, displaying an emerald green badge declaring
  `[SUNSET SEAL COMPLETE] :: SHIFT ARCHIVED FOR day-xxx`, proving the shift is
  securely frozen to main.

If a critical downstream regression occurs, the Sunset Seal architecture
provides a mathematically verifiable rollback path. The operator does not guess
which random commit is safe; they revert to the last certified `.sealed`

- **Console Projection (`cns00`):** The terminal streams the exact workday
